# Архитектура подключаемых источников данных

Дата: 4 ноября 2026 года. Статус: уточнённый архитектурный контракт для реализации. Код адаптеров ещё не написан; реальные подключения не проверены.

## 1. Результат проверки

Общая схема «адаптер → нормализованные данные → engine → событие → уведомление» подходит. Для удобного расширения её недостаточно описывать одним названием DataProvider: нужны явные идентичности, необязательные возможности, единые ошибки, владельцы восстановления и общий набор контрактных тестов.

Новый поставщик обычных OHLCV/котировок добавляется отдельным модулем и регистрацией. Для него не должны требоваться новые ветки в редакторе, engine, Telegram, таблицах БД или экране пары. Работа по пониманию внешнего API и его проверке остаётся необходимой; заранее обещать одинаковую сложность любого неизвестного API нельзя.

## 2. Три независимые сущности

| Сущность | Смысл | Пример |
|---|---|---|
| Пара (Pair) | Пользовательская рабочая область со своими сигналами и историей событий | «Евро / доллар» |
| Подключение (Connection) | Тип провайдера, окружение, название, конфигурация, ссылки на секреты и доступ | «iTick · Forex», «Finam · Основной» |
| Привязка инструмента (InstrumentBinding) | Сопоставление пары с проверенным инструментом конкретного подключения | iTick: region/code; Finam: собственный symbol/площадка |

Сигнал принадлежит Pair и использует активную привязку пары. SignalDefinition содержит параметры/условия/периоды, а не Finam symbol, iTick region или URL API. Название EUR/USD не служит универсальным идентификатором поставщика и не доказывает эквивалентность spot/CFD/фьючерса.

У пары может храниться несколько привязок для разных подключений, но в рабочей области активна одна. Несколько подключений можно сохранить одновременно; разные пары могут использовать разные источники. Объединение данных разных поставщиков внутри одного сигнала в первой версии не требуется.

## 3. Переключатель источника в самом терминале

В шапке выбранной пары рядом с её названием и периодом располагается dropdown **«Источник: Finam ▾»**. Список строится из зарегистрированных и настроенных подключений, а не из двух жёстко заданных кнопок. При нескольких подключениях одного типа видны их пользовательские названия. В списке есть переход «Настроить подключения»; недоступность подключения/инструмента показывается с причиной.

```text
EUR/USD    Источник: [Finam · Основной ▾]    5m 15m 1h 1d
                      iTick · Forex
                      Настроить подключения…
```

Переключение применяется **к выбранной паре**, её графику и всем её включённым сигналам. Другие пары продолжают работать. Оно не меняет состав условий, индивидуальные флаги включения или Telegram-маршрутизацию. Новый провайдер появляется в этом списке через тот же реестр.

До начала обработки на новом источнике проверяются привязка инструмента, права и совместимость нужных периодов/полей. Неоднозначный код требует сопоставления, а не угадывается по имени пары. При переходе график/сигналы получают видимый статус «Переключение / прогрев»; незавершённые цепочки сбрасываются с причиной. Загружается история нового ряда, после готовности начинаются новые проверки без уведомлений за прошлое. Отложенные сообщения старого подключения отсекаются по версии активной привязки/подписки.

При ошибке выбранного источника UI показывает ошибку; свечи другого источника молча не подставляются. Возврат к прежнему поставщику — явное действие пользователя. У старых событий и доставок сохраняется прежний источник; текущий dropdown не переписывает происхождение истории.

## 4. Реестр и интерфейс адаптера

Каждый модуль предоставляет описание: стабильный `providerType`, версия адаптера, название, схема настроек, описания обычных/секретных полей и фабрика создания экземпляра. Приложение использует общий реестр и общий экран настройки; секреты доступны только backend-части.

| Операция | Обязательность и результат |
|---|---|
| Подключить/проверить/закрыть | Жизненный цикл и типизированный статус, без формата ошибок конкретного SDK наружу |
| Получить capabilities | Фактические возможности подключения и выбранного инструмента, с учётом прав/пакета |
| Найти инструменты | Необязательно; при отсутствии каталога поддерживается ручная привязка с проверкой |
| Разрешить/проверить код | Метаданные инструмента или явная ошибка/непроверенная возможность |
| Получить страницу истории | Ряд за общий интервал, нормализованные бары, курсор, фактический охват, признак неполноты |
| Подписаться на бары | Необязательно; обновления/исправления/качество/статус и освобождение подписки |
| Подписаться на котировки | Необязательно; используется для UI, не выдаётся автоматически за OHLCV |
| Получить календарь | API-календарь либо явно заданная проверенная политика; отсутствие расписания не означает 24/7 |

Общий запрос истории использует UTC и интервал `[from, to)`. Параметры `et`, `limit`, cursor, порядок и включительность границ переводит адаптер. Страница сообщает, остались ли данные, их фактический диапазон и продолжение; пустой ответ не означает автоматически, что прогрев полон. Длинные загрузки поддерживают отмену и прогресс, чтобы устаревший ответ не попадал в уже переключённую пару.

Источники с REST-only работают через общий планировщик опроса истории. Отсутствие свечного WebSocket не ломает конструктор. Quote-only поток даёт живую цену, но без доказанной полноты сделок не заменяет бары. Источник, неспособный предоставить нужные данные даже через разрешённую агрегацию, показывает несовместимость конкретного сигнала.

Здесь не требуется универсальный DSL для внешних HTTP API, собственная сеть микросервисов или пользовательская загрузка исполняемых плагинов. Новый адаптер — обычный TypeScript-модуль внутри приложения, зарегистрированный при сборке.

## 5. Возможности определяются данными и доступом

Capabilities уточняются после подключения и при изменении доступа; они зависят от инструмента и канала, а не только от имени поставщика. В них входят:

- Наличие каталога/истории/барового потока/котировок, доступные периоды и вычисляемые периоды.
- Глубина/пагинация истории, квоты и область их учёта, лимиты подписок/соединений, доступная задержка.
- Часовой пояс, календарь и выравнивание баров; политика определения закрытия и исправлений.
- Вид цены (trade/bid/ask/mid/другой), единицы/смысл объёма, корректировки, отсутствующие поля и качество.

Нехватка объёма — это не `volume=0`. Отсутствие расписания или подтверждения закрытия также не маскируется фиктивными значениями. Общая проверка совместимости сопоставляет требования схемы с capabilities до запуска. Изменение прав или потеря канала отражается в состоянии соответствующих пар, не останавливая остальные подключения.

## 6. Где выполняется общая работа

| Слой | Ответственность |
|---|---|
| Адаптер поставщика | Авторизация/обновление сессии, внешние методы/SDK, heartbeat и протокол подписок, перевод полей/ошибок, правила происхождения и закрытия свечей |
| Общий сервис рыночных данных | Лимитер с политикой квоты адаптера, retry/планирование восстановления, общий кеш, дедупликация, проверка качества, совместное использование подписок, backfill и сшивка истории/потока |
| Общий календарь/агрегатор | Вычисляемые периоды и пропуски по объявленной календарной политике; синхронизация периодов |
| Engine | Только вычисления на предоставленных рядах, состояние правил и SignalEvent; не делает сетевых запросов |
| ChartBridge | Перевод общих данных в KLineCharts, загрузка через сервис/IPC и отображение; нет импортов Finam/iTick или их токенов |
| NotificationChannel | Доставка готового события с происхождением; не знает транспорт данных |

Retry и реконнект имеют одного владельца — общий сервис, который запрашивает у адаптера восстановление нужного канала. Если внешний SDK уже автоматически повторяет операции, это отключается либо явно согласуется в адаптере. Независимые циклы SDK + адаптер + приложение не должны умножать запросы.

Ошибки приводятся к категориям `unauthorized`, `forbidden`, `rateLimited`, `disconnected`, `unavailable`, `invalidRequest`, `unsupported`, `invalidData`. Для них известны повторяемость, `retryAfter`, область действия и безопасная диагностика. Finam Authorization и iTick token/разные коды REST/WS остаются только внутри адаптеров. Приложение не проверяет наружу `code == 0` для всех источников.

## 7. Хранение и происхождение

Каждый набор данных получает `datasetId`, связанный с подключением/окружением, точным инструментом, источником цены/объёма, корректировками, календарём, native/derived и версией правил агрегации. Бары и индикаторные кеши используют этот ID и таймфрейм; изменение значимых свойств создаёт новый набор и прогрев.

Схема SQLite общая: connections, instrument bindings, datasets, bars, схемы/назначения, checkpoint, события и outbox. Новому поставщику не нужна таблица `finam_bars`/`itick_bars` или колонка для каждого vendor-поля. Специфичная конфигурация хранится версионированным JSON, секреты — отдельными ссылками. Исходные поля для диагностики, если сохраняются, изолированы от вычислительной модели и очищены от секретов.

NormalizedCandle содержит Decimal-строки OHLCV, время начала/закрытия/получения, состояние закрытия, ревизию и качество. Правило закрытия и его основание записаны в метаданных; последнее поле close из ответа не принимается за доказательство финальности. Общий сервис сохраняет происхождение и проверяет монотонность/перекрытия/дубли. Поздние исправления не маскируются обычным новым баром.

## 8. Как добавить следующий API

1. Описать доступные поля/периоды/каналы, авторизацию, календарь, квоты и ограничения.
2. Реализовать адаптер с переводом внешнего формата в общий контракт; использовать готовый SDK, если он подходит, иначе обычные HTTP/WebSocket-клиенты.
3. Добавить описание настроек/секретов и одну регистрацию фабрики в реестре.
4. Добавить обезличенные протокольные фикстуры и выполнить общий контрактный набор.
5. Проверить реальный доступ, сшивку, закрытие свечей и рабочий сценарий пары; зафиксировать фактические capabilities.

Это расширение не меняет AST, формулы индикаторов, логику групп/таймфреймов, Telegram, основной экран или схему хранения баров. Если новый API приносит новую предметную сущность, например опционы со специальными полями вместо OHLCV, она добавляется общим расширением модели, а не скрытым исключением для vendor.

## 9. Архитектурная приёмка

- Уже в фазе 0 контракты проверяются на разных формах доступа; в фазе 1 ReplayProvider использует тот же интерфейс. Затем Finam и iTick реализуют его без изменения core/UI.
- Тестовый третий адаптер: REST-only, без каталога и объёма, с другим временем бара/пагинацией. Его регистрация должна работать с ручной парой и ценовой схемой; объёмное условие должно честно показать несовместимость. Тест не требует третьего настоящего аккаунта.
- Дополнительные проверки: права на kline изменились; одинаковый тикер разных площадок; разные окружения; смена источника при позднем ответе; разрыв потока с backfill; смена цены bid/mid; отдельная ошибка одного подключения.
- Raw-фикстуры адаптеров и независимые ожидаемые нормализованные данные проверяются до engine. Затем общий поток проверяется через схемы и тестовый канал. Одинаковые нормализованные данные дают одинаковый результат; равенство реальных котировок разных источников не предполагается.
- В CI проверяются границы импортов: providers не попадают в domain/rules/indicators, renderer и notifications. ChartBridge использует общий сервис, а не создаёт второй клиент API.
- Критерий удобства расширения: новый типичный источник подключается изменениями в собственном модуле, его регистрации и тестах; необходимость править сигналы/Telegram/основную БД означает нарушение границ и требует исправления архитектуры.
