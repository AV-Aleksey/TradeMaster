# iTick — альтернативный источник данных

Дата проверки документации: 4 ноября 2026 года. Статус: добавлен в требования и план; адаптер пока не реализован, проверка с токеном не выполнялась.

## Назначение

iTick подключается отдельным `DataProvider` наряду с Finam. REST используется для каталога, истории и сверки; WebSocket — для обновлений выбранной пары. Конструктор, расчёты сигналов и доставка уведомлений используют общие контракты и не зависят от выбранного API.

В настройках можно сохранить подключения обоих поставщиков. У пары/её рабочего назначения явно выбран один источник; параметры его возможностей показываются рядом. Одни пары могут использовать Finam, другие — iTick. При смене источника сопоставляются коды, сбрасываются незавершённые цепочки и выполняется новый прогрев; схема и Telegram-настройки сохраняются. Автоматического переключения между источниками и смешивания их свечей внутри ряда в первой версии нет.

## REST

| Задача | Метод | Применение |
|---|---|---|
| Каталог и поиск пары | `GET /symbol/list?type=forex&region=GB` с необязательным `code` | Загрузка доступных кодов и проверка ручного добавления |
| Последний tick | `GET /forex/tick?region=GB&code=EURUSD` | Последняя цена/сделка для отображения, не полная история OHLCV |
| Свечи | `GET /forex/kline` | История, прогрев, восстановление и сверка |

Присланное пользователем описание каталога фиксирует поля `c` (код), `n` (имя), `t` (тип), `e` (площадка). Тип/регион запроса и эти поля преобразуются в общий справочник инструментов; дополнительные поля ответа не становятся обязательными без контракта. Поиск в UI берёт коды из API, не требует вручную заполнять все пары. Ручной ввод остаётся альтернативой с проверкой. [Каталог iTick](https://docs.itick.io/en/rest-api/basics/symbol-list).

В запросе свечей используются `region`, `code`, `kType`, `limit` и `et` для окончания выборки. Периоды forex: 1m, 5m, 15m, 30m, 1h, день, неделя, месяц; 10m строится общим агрегатором. Соответствие `kType` преобразуется внутри адаптера, а не хранится вместо общего ID таймфрейма. Фактические границы дневной свечи проверяются отдельно. [Свечи iTick](https://docs.itick.io/en/rest-api/forex/forex-kline).

Токен передаётся в заголовке `token` и хранится с той же системной защитой, что ключ Finam. Production-адреса в документации: `https://api.itick.io`, WebSocket forex — `wss://api.itick.io/forex`; trial использует `api-free.itick.io`. Окружение выбирается в подключении, его данные и кеши различаются. [Адреса API](https://docs.itick.io/en/api-url), [REST tick](https://docs.itick.io/en/rest-api/forex/forex-tick).

## WebSocket

Авторизация, subscribe/unsubscribe и heartbeat реализуются внутри адаптера. Пара кодируется как `symbol$region`; доступны quote/tick и свечной канал. Для текущей свечи предпочтителен kline, а не восстановление OHLCV из отдельных REST-снимков tick. Поддержка конкретных каналов/периодов и число подписок зависят от доступа.

**Тарифное ограничение:** опубликованная документация разрешает `kline@1` для Premium и выше либо при наличии пакета фондовых данных. Доступ к quote/tick сам по себе не доказывает доступ к свечной подписке. Есть heartbeat с рекомендацией интервала не реже 30 секунд; потеря связи требует восстановления подписок и сверки с REST. [Forex WebSocket](https://docs.itick.io/en/websocket/forex).

Если свечной канал недоступен, интерфейс показывает ограничение. REST-обновление возможно в пределах фактической квоты с обозначением периодического режима. Агрегация потока tick допускается только после отдельной проверки его полноты/семантики; это не автоматическая равноценная замена kline.

## Нормализация и возможности

- Идентичность включает provider/connection/environment/region/code. Кеш iTick не дополняется свечами Finam с тем же отображаемым именем.
- OHLCV и время переводятся в общую модель без промежуточного округления цен; при необходимости числовых JSON-значений применяется готовый lossless-парсер. Числа для графика формируются только на границе визуализации.
- Объём свечи, объём отдельного tick и дневной объём quote не взаимозаменяемы. Смысл и единицы forex-объёма проверяются на доступном потоке; неизвестное значение не выдаётся за сопоставимый биржевой объём.
- В рассмотренных примерах свечей нет явного флага закрытия. Адаптер должен проверить timestamp, расписание, окончательность, запоздавшие исправления и сверку; получение поля `c` само по себе не означает `closed=true`.
- REST- и WS-коды успеха проверяются раздельно: в опубликованных примерах REST успешен при `code=0`, служебные WS-ответы — при `code=1`. HTTP 200 не заменяет проверку прикладного результата.
- Capabilities содержат фактические периоды/каналы, глубину истории, квоты, задержку, календарь и пригодность объёма. Лимит Finam 200 запросов/мин не переносится на iTick. [Структура свечей](https://docs.itick.io/en/kline), [ошибки iTick](https://docs.itick.io/en/error-code).

## План и тесты

До появления токена: реализовать контрактный каркас и тесты iTick на фикстурах REST каталога/tick/kline и WS auth/subscribe/bar/error/heartbeat; фикстуры без секретов и с явной отметкой происхождения.

При появлении доступа: проверить каталог EURUSD, историю разных периодов, границы/объём свечей, права на kline, trial/production, квоты, реконнект и отсутствие дублей при сшивке. Проверка iTick не ждёт Finam и наоборот; оба используют общий набор контрактных тестов DataProvider.

Приёмка: одинаковые нормализованные входы через Finam- и iTick-адаптеры дают одинаковые результаты core и уведомления. Реальные ряды разных источников сравниваются как разные данные; совпадение реальных событий не обещается. Детальный порядок добавлен в [план реализации](IMPLEMENTATION_PLAN.md).
