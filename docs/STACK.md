# TradeMaster — выбор стека

Дата: 4 ноября 2026 года. Статус: предлагаемое решение для первой версии.

## Решение

Разрабатывать desktop-приложение на **Electron + React + TypeScript**. Первый поставщик данных — **Finam Trade API**. Движок индикаторов и правил — отдельный пакет TypeScript, общий для мониторинга и проверки на истории.

В план также включён альтернативный поставщик **iTick (REST + WebSocket)**. Оба адаптера реализуют один DataProvider; источник выбирается для пары без изменения схем и уведомлений. Контракты и ограничения: [ITICK.md](ITICK.md).

Для следующих API зафиксированы реестр адаптеров, Pair/Connection/InstrumentBinding, общий MarketDataService и ChartBridge, capabilities с учётом прав, общие ошибки и datasetId. Каждый поставщик реализуется обычным TypeScript-модулем; REST/WebSocket/SDK остаются его внутренней деталью. Переключатель источника и форма настроек строятся из реестра. Полный контракт и критерий добавления API без правок core/UI/БД: [DATA_SOURCES.md](DATA_SOURCES.md).

Это инженерный выбор под текущие требования: вложенный конструктор условий, график, локальное хранение, Telegram, macOS и Windows. Python из исходного README не является обязательным: готового Python-движка в проекте сейчас нет.

Главный архитектурный приоритет — независимый от поставщика конструктор: таблицы показателей/таймфреймов/инструментов → декларативная схема И / ИЛИ → единый движок → универсальное событие → канал уведомлений. Одна схема использует разные таймфреймы. Finam реализует контракт источника данных, а не определяет модель правил. Замена API меняет адаптер и сопоставление инструментов, сохраняя схему и Telegram-настройки.

| Задача | Технология | Применение |
|---|---|---|
| Desktop и системные функции | Electron | Окна, трей, управление процессами, доступ к защищённому хранению |
| Язык | TypeScript, strict mode | Интерфейс, AST правил, адаптеры, движок |
| Интерфейс | React + Ant Design (`antd`) + `@ant-design/icons` | Готовые таблицы, формы, настройки, диалоги, панели, журнал |
| Конструктор условий | React Query Builder + `@react-querybuilder/antd` | Готовый редактор вложенных групп И / ИЛИ, расширяемые поля и операции |
| Сборка | electron-vite + npm | Разработка main, preload, renderer и engine-пакетов |
| График | KLineCharts (`klinecharts`) | Свечи, панели индикаторов, масштабирование, курсор, overlays и live-обновления |
| Finam, первая версия | REST/HTTPS + WebSocket BARS | REST: авторизация, справочник, история и сверка; WebSocket: живой график выбранной пары |
| Finam, альтернативный транспорт | gRPC | Возможная замена транспорта через тот же контракт адаптера |
| iTick, альтернативный источник | REST/HTTPS + WebSocket forex | Каталог пар, история kline, live-каналы согласно тарифу; независимый адаптер |
| Контракты Finam | REST-схемы и runtime-валидация | Изоляция внешнего API от модели свечей и правил |
| Telegram | HTTPS Bot API | Привязка через личного бота и отправка сообщений |
| Хранилище | SQLite + better-sqlite3, SQL-миграции | Справочники, версии схем, свечи, события, очередь уведомлений |
| Десятичные вычисления | decimal.js | Цены, объёмы, индикаторы, сравнения |
| Валидация | Zod | IPC, импорт схем, настройки, нормализованные данные |
| Проверки | Vitest + Playwright | Обязательная регрессия индикаторов/сигналов по отдельности и совместно, полный процесс и редактор |
| Установщики | electron-builder | macOS DMG и Windows installer |

Версии пакетов фиксируются совместимым набором в lockfile при создании каркаса. Используется поддерживаемый стабильный Electron; prerelease-зависимости по умолчанию не берутся. Среда разработки Node.js выбирается по требованиям сборщика и не подменяет встроенную среду Electron.

## Приоритет готовых решений

Пользовательский приоритет: обычный рабочий инструмент с минимумом собственной инфраструктуры и ручной реализации UI. Размер приложения и преждевременная оптимизация вторичны. Для экранов используем один готовый UI-kit, для редактора условий и финансового графика — профильные библиотеки. CSS Modules допустимы для размещения и небольших поправок, но не для повторной реализации кнопок, таблиц и форм.

**Ant Design** выбран под таблицы справочников, формы и панельную компоновку терминала. Table предоставляет сортировки/фильтры и пагинацию; Form — управление формой; Splitter — изменение размеров рабочих областей. Тёмная компактная тема и янтарный акцент задаются через ConfigProvider и токены темы. [Table](https://ant.design/components/table/), [Form](https://ant.design/components/form/), [Splitter](https://ant.design/components/splitter/), [тема](https://ant.design/docs/react/customize-theme/).

**React Query Builder** предоставляет интерфейс вложенных групп условий и официальную интеграцию с Ant Design. Он используется как редактор, с преобразованием в наш SignalDefinition; его формат не становится единственным контрактом хранения. Таймфреймы, ссылки на индикаторы, окна/цепочки и объяснение событий остаются предметной моделью TradeMaster, а не автоматически готовыми функциями обычного query builder. [Официальные интеграции](https://react-querybuilder.js.org/docs/compat).

**KLineCharts** выбран вместо первоначального Lightweight Charts с учётом приоритета готовых функций: у него есть встроенные технические индикаторы, отдельные панели и модели рисования, расширяемые индикаторы и подключение истории/live-данных. Небольшая React-обёртка управляет жизненным циклом экземпляра и связывает его с общим DataProvider. Кнопки выбора периода/индикаторов выполняются компонентами Ant Design; сам график не является готовым целым экраном терминала. [Возможности](https://klinecharts.com/en-US/guide/introduction), [индикаторы](https://klinecharts.com/en-US/guide/indicator), [данные](https://klinecharts.com/en-US/guide/data-integration).

Расчёты значений, участвующих в сигналах, имеют единый источник в core. Настроенный MACD WMA/WMA и Stochastic из README отображаются через расширение индикаторов KLineCharts с теми же данными/формулами; встроенные MACD/KDJ не считаются автоматически эквивалентными. Передача уже рассчитанных рядов и live-обновлений проверяется в первом прототипе интеграции. Форматы данных графика используют number только на границе отображения; хранение, сравнения и расчёт сигналов сохраняют Decimal. [Пользовательские индикаторы](https://klinecharts.com/api/chart/registerIndicator).

Готовые компоненты не заменяют адаптер Finam, синхронизацию разных периодов, автомат временных подтверждений и надёжную доставку. Эти части составляют логику продукта. Готовые вычислительные библиотеки допускаются после проверки формул и семантики; собственные альтернативы коробочным компонентам без конкретной причины не создаются.

## Почему Electron

Конструктор — форма с рекурсивными группами условий, поэтому React подходит без отдельного графического редактора. Общий TypeScript позволяет использовать одну модель правил и один вычислитель в live, replay и бэктесте.

У Electron есть отдельные utility-процессы: расчёты и сетевые подключения можно вынести из процесса интерфейса. Это подтверждённая возможность платформы; конкретное разделение процессов описано в [ТЗ](SPEC.md). [Документация Electron](https://www.electronjs.org/docs/latest/tutorial/process-model).

Цена выбора — собственный Chromium в поставке, расход памяти и необходимость регулярно обновлять Electron. Приложение не должно создавать отдельный процесс или график на каждый инструмент.

| Вариант | Оценка для проекта |
|---|---|
| **Electron + TypeScript** | Основной выбор: единая модель схем и вычислений, web-интерфейс внутри desktop |
| Tauri + Rust | Альтернатива при приоритете размера и системной интеграции; потребует Rust-часть и контракты между языками |
| Tauri + Python sidecar | Технически допустим, но добавляет упаковку Python и управление дополнительным runtime; готового ядра для переиспользования пока нет |
| Python + Qt | Возможен, но для выбранного интерфейса и web-графика предпочитаем React; возвращаться к нему стоит при появлении существенного Python-кода |

Tauri действительно поддерживает упаковку внешних бинарников, включая Python, но требует сборки для целевых архитектур. Это не запрет на альтернативу, а дополнительная работа по поставке. [Документация Tauri](https://v2.tauri.app/develop/sidecar/).

## Особенности Finam

Finam — брокерский источник данных, поэтому модель приложения использует **инструменты**, а не только валютные пары. Идентичность включает поставщика, площадку и собственный идентификатор; отображаемый тикер не служит уникальным ключом.

После отдельной проверки REST выбор уточнён: для первой версии с анализом закрытых свечей достаточно REST и планировщика запросов `Bars`. Авторизация, каталог и расписание также доступны по REST. Это заключение по контрактам, а не результат нагрузочного испытания с реальным токеном. Подробности: [оценка REST](FINAM_REST.md).

После уточнения требования к живому графику WebSocket BARS включён в первую версию для выбранной пары. REST остаётся источником истории, сверки и запланированных обновлений фоновых рядов. gRPC с генерируемым клиентом и обновлением сессии остаётся допустимой альтернативой, но обязательной зависимости от него в MVP нет. Core, конструктор и Telegram не должны различать REST polling и server stream. [REST Finam](https://api.finam.ru/docs/rest/), [WebSocket Finam](https://api.finam.ru/getting-started/bystryy-start/poluchat-dannye-cherez-websocket/).

В опубликованной модели `Bar` нет отдельного поля закрытия свечи. До реализации сигналов нужно проверить способ финализации, включая последнюю свечу торговой сессии. Переход времени на следующий интервал сам по себе не принимается за доказательство окончательности данных. [Официальный protobuf MarketData](https://github.com/FinamWeb/finam-trade-api/blob/main/proto/grpc/tradeapi/v1/marketdata/marketdata_service.proto).

По опубликованному контракту глубина истории M5 ограничена 30 днями. Поэтому требование старого README о трёх месяцах 5m нельзя обещать через один запрос к Finam: нужны накопление локального архива, импорт CSV или другой источник. Доступность и актуальные ограничения проверяются при подключении. [Описание таймфреймов Finam](https://raw.githubusercontent.com/FinamWeb/finam-trade-api/main/proto/grpc/tradeapi/v1/marketdata/marketdata_service.proto).

## Хранение и изоляция

SQLite размещается в каталоге данных приложения. Основной writer — процесс движка; бэктест читает фиксированную выборку и передаёт результаты через IPC. Для конкурентного чтения используется WAL с контролем checkpoint. [SQLite WAL](https://www.sqlite.org/wal.html).

better-sqlite3 — нативная зависимость: совместимость с ABI Electron и упаковка проверяются на каждой целевой платформе в самом начале. [Проект better-sqlite3](https://github.com/WiseLibs/better-sqlite3).

Секреты сохраняются как зашифрованные значения через Electron `safeStorage`: на macOS ключ защищает Keychain, на Windows — DPAPI. SQLite содержит только ссылку на секрет. На Windows это не обеспечивает изоляцию от всех программ того же пользователя. Если системное шифрование недоступно, секрет используется только до закрытия приложения. [Electron safeStorage](https://www.electronjs.org/docs/latest/api/safe-storage/).

По умолчанию UI видит маску и статус ключа. По требованию пользователя глазок в настройках получает сохранённый ключ через отдельную проверяемую IPC-команду; ключ отсутствует в общих снимках состояния и очищается из просмотра при скрытии/закрытии настроек. При первоначальном вводе поле передаёт значение через IPC-метод сохранения и очищается. Сеть, расшифровка и запись файлов выполняются вне renderer. Применяются `contextIsolation`, sandbox, отключение Node integration и проверка IPC. [Electron Security](https://www.electronjs.org/docs/latest/tutorial/security/).

## Что проверить до основной разработки

1. Установщик запускается на macOS Apple Silicon и Windows x64 без установки Node.js пользователем; матрица Intel Mac уточняется отдельно.
2. Finam: REST-вход, права на данные и задержка, обновление сессии, история и периодическое получение новых свечей одного доступного инструмента, восстановление после ошибки. Поток проверяется отдельно, если включён в релиз.
3. Подтверждён способ получения закрытых свечей, включая конец сессии и поздние исправления; при необходимости — сверка с историческим API.
4. SQLite и safeStorage работают в упакованных сборках, а не только в dev-режиме.
5. Вложенный редактор сохраняет схему, которую тот же engine выполняет на тестовой истории.

Эти проверки подтверждают пригодность стека. Они не требуют изменения торгового счёта или отправки ордеров.

## Поставка и ограничения библиотек

Выбранные UI-пакеты: Ant Design — MIT, React Query Builder и его Ant Design-интеграция — MIT; KLineCharts — Apache-2.0. Лицензии и уведомления включаются в поставку. Lightweight Charts остаётся резервной альтернативой и не ставится одновременно без необходимости. [Ant Design](https://github.com/ant-design/ant-design/blob/master/LICENSE), [React Query Builder](https://github.com/react-querybuilder/react-querybuilder/blob/main/packages/antd/package.json), [KLineCharts](https://github.com/klinecharts/KLineChart).

Сборку процессов организует electron-vite; установщики — стабильная версия electron-builder. Для выпуска macOS предусматриваются подпись и notarization, для Windows — подпись релизного установщика. Учётные записи и сертификаты выпуска не создаются автоматически. [electron-vite](https://electron-vite.org/guide/), [electron-builder](https://www.electron.build/), [подпись Electron](https://www.electronjs.org/docs/latest/tutorial/code-signing).

Playwright помечает поддержку Electron как experimental: критические проверки движка не должны зависеть от неё, а релиз дополняется проверкой упакованных приложений. [Playwright Electron](https://playwright.dev/docs/api/class-electron).

Vitest проверяет весь критический контур сигналов без сети: независимые эталоны индикаторов, операторы, вложенные группы, временные цепочки, разные таймфреймы, изоляцию пар/сигналов, восстановление и эквивалентность отдельного/совместного прогона и live-replay/бэктеста. Playwright дополняет его проверками создания и сохранения схем в UI. Регрессионный набор — обязательный CI-барьер для изменений и выпуска. Требования к матрице сценариев и эталонам: [SPEC.md, раздел 13.2](SPEC.md#132-обязательные-тесты-сигналов).

Для десятичной арифметики используется decimal.js с явно зафиксированными точностью и округлением. Zod валидирует JSON-контракты в runtime; TypeScript сам по себе этого не делает. [decimal.js](https://mikemcl.github.io/decimal.js/), [Zod](https://zod.dev/).
