# Применимость Finam REST к TradeMaster

Проверено 5 ноября 2026 года с сохранённым пользовательским ключом. Реализован адаптер REST + WebSocket BARS через общий `DataProvider`; движок сигналов и Telegram остаются общими. Состав экранов: [UI.md](UI.md).

## Реализованное подключение

- JWT хранится только в памяти backend, запросы авторизации объединяются; обновление по `expires_at` с запасом 60 секунд, один повтор REST после 401. Срок сравнивается с HTTP Date Finam и монотонным временем процесса; при отсутствии заголовка серверное время запрашивается через Clock с JWT для каждой новой сессии. Локальный сдвиг часов не вызывает ложное «сессия уже истекла». Реально просроченная новая сессия запрашивается повторно один раз, затем возвращается явная ошибка. Ping каждый раз получает свежую сессию и подтверждает авторизацию, не включает мониторинг и не возвращает JWT/номера счетов в UI.
- `AllAssets` с пагинацией, кешем на пять минут и поиском по тикеру/названию. Непригодные записи без тикера/MIC пропускаются. Точный `ticker@MIC` проверяется через `GetAsset` с `account_id` из сессии (без него фактический сервер отвечает 400). Первичная загрузка полного каталога может занимать несколько минут; точный поиск обходит её.
- Пара хранит тикер и MIC отдельно. В каталоге отображается площадка, регион GB для Finam не подставляется. Добавление подтверждается сервером. Переход Finam ↔ iTick/Replay требует добавления инструмента из нужного каталога, поскольку совпадение кодов не подтверждает идентичность инструментов.
- REST Bars: 1m/5m/15m/30m/1h/1d, запрос в пределах опубликованной глубины, decimal без преобразования цен в Number, OHLCV проверяется. 10m собирается общим сервисом из 5m. Очередь Bars общая для всех рядов Finam, интервал между запросами 350 мс; отдельные очереди остальных методов.
- WebSocket: рукопожатие, подписка BARS, heartbeat, ограничение времени подключения, переподключение с backoff, переоткрытие перед истечением JWT. Ошибки envelope и `payload.error` ведут к восстановлению; ошибки авторизации сбрасывают JWT. Существующий сервис продолжает REST-сверку каждые 30 секунд при активном графике/мониторинге.
- Потоковые свечи всегда предварительные; только REST-ряд с более поздней свечой подтверждает закрытие предыдущих. Последний бар не закрывается по локальным часам или `is_data_snapshot`, в том числе после конца сессии. Поэтому последний сигнал перед перерывом может ждать следующей свечи. Календарная финализация и проверка поздних исправлений ещё впереди.

Ключ хранится в `credentials-finam.enc` через Electron safeStorage; ключ iTick — отдельно в `credentials.enc`. Смена ключа доступного источника перезапускает подключения и прогрев, мониторинг после перезапуска выключен. Секреты и JWT не входят в снимки состояния, фикстуры или логи.

## Проверка с реальным доступом

- Auth/TokenDetails: успешно.
- Дополнительная проверка валют выявила ошибку фильтра: площадка `#WWCP` отбрасывалась из-за символа `#` в MIC. Исправлены валидаторы адаптера и IPC, добавлен регрессионный тест. Предыдущие 21 результат поиска EUR/USD не были полным набором подходящих инструментов.
- С пользовательским ключом подтверждены свежие 5m-свечи и LastQuote для `EURUSD@#WWCP`, `GBPUSD@#WWCP`, `USDJPY@#WWCP`, `USDCHF@#WWCP`, `USDCAD@#WWCP`, `EURJPY@#WWCP`, `EURGBP@#WWCP`, `USDRUB@#WWCP`, `EURRUB@#WWCP`, `CNYRUB@#WWCP`. Это отдельные источники котировок; единицы/смысл сообщаемого Forex-объёма ещё не подтверждены.
- На MISX свечи получены для CNYRUB_TOM, BYNRUB_TOM, TRYRUB_TOM, KZTRUB_TOM, AMDRUB_TOM, KGSRUB_TOM; для ряда этих инструментов последняя сделка существенно реже текущего времени. У HKDRUB_TOM/AEDRUB_TOM/TJSRUB_TOM свежих свечей нет, у UZSRUB_TOM последние свечи датированы 2 ноября. Наличие в каталоге и успешный ответ котировки без цены не подтверждают живой график.
- `EUR/USD@_NPRO` и его TOD/TOM-варианты по-прежнему без свечей и last/bid/ask; старые MOEX EURUSD000TOM/TOD содержат котировки 2025 года. Их не следует выбирать вместо работающего `EURUSD@#WWCP`.
- `SBER@MISX` и `EURUSD@#WWCP`: получено по 120 свечей всех шести нативных периодов, включая сообщаемый объём, и принят WebSocket BARS.
- Фактический WS `payload` приходит JSON-строкой с вложенными decimal-объектами. Адаптер принимает эту форму и объект со строковыми decimal из официального описания. Публичные образцы REST и WS сохранены в `tests/fixtures/finam`, без авторизации и данных счёта.
- Live-проверка не является приёмкой торгового календаря, задержки публикации, финальности последнего бара сессии или работы после длительного обрыва.

Повторяемая read-only проверка из dev-профиля: `npm run probe:finam` (по умолчанию SBER@MISX). Другой инструмент: `FINAM_SYMBOL='SBER@MISX' npm run probe:finam`; полный поиск: `FINAM_QUERY=EURUSD npm run probe:finam`. Ключ читается через safeStorage; при необходимости `TRADEMASTER_DATA_DIR` задаёт каталог, а `FINAM_TOKEN` — локальную переменную среды. Не передавайте ключ в аргументе команды. Проверка завершается ошибкой при пустой истории или отсутствии свежих потоковых данных за 20 секунд. Ордеров и запросов портфеля нет.

## Вывод

**REST подходит для первой версии конструктора сигналов на закрытых свечах, включая разные таймфреймы в одной схеме.** Рекомендуемый старт — история и обновления через `Bars`, локальные индикаторы и планировщик опроса по ожидаемым закрытиям. Для непрерывного обновления живого графика используется потоковая подписка через тот же адаптер.

Это инженерный вывод при условии проверки задержек, прав пользователя и завершённости свечей. Обязательный выбор gRPC в первоначальном варианте STACK.md был преждевременным.

## Какие методы нужны

| Задача | Метод из переданного пользователем справочника | Использование в приложении |
|---|---|---|
| Войти по API-секрету | Auth / TokenDetails | Получить сессию, проверить права и срок |
| Загрузить свечи | Bars | Основной источник для MACD, Stochastic, EMA и объёма |
| Заполнить справочник | Assets / AllAssets / GetAsset / Exchanges | Поиск и проверка вручную добавленных инструментов |
| Учесть торговые часы | Schedule / Clock | Границы свечей, перерывы, выходные, часы сервера |
| Проверить параметры | GetAssetParams | Метаданные доступного инструмента |
| Наблюдать за квотами | GetUsageMetrics | Диагностика вместе с собственным ограничителем частоты |
| Показать последнюю цену | LastQuote | Дополнительная функция интерфейса |
| Показать последние сделки | LatestTrades | Необязательная лента, не замена OHLCV |

Finam не вычисляет наши пользовательские схемы: индикаторы, И / ИЛИ, окна и объединение таймфреймов выполняются локально. Ордера и отчёты счёта для текущего объёма не нужны.

`Bars` принимает один инструмент, таймфрейм и интервал. Нативные 5m/15m/30m/1h/1d позволяют загрузить ряды для одной смешанной схемы; 10m требуется строить отдельно. В опубликованном описании глубина M5–H8 — 30 дней, дневного периода — 365 дней. [REST API](https://api.finam.ru/docs/rest/#marketdataservice_bars).

`LatestTrades` возвращает последние сделки. В его опубликованном запросе есть только symbol, без курсора восполнения пропущенной ленты: восстановление всей истории сделок и полного OHLCV по последовательным снимкам этим контрактом не гарантируется. Поэтому строить основную историю свечей из периодического `LatestTrades` не следует. [Контракт MarketData](https://github.com/FinamWeb/finam-trade-api/blob/main/proto/grpc/tradeapi/v1/marketdata/marketdata_service.proto).

## Оценка нагрузки

Finam указывает **200 запросов в минуту на метод**, а не единый лимит всех методов вместе. Все инструменты и таймфреймы `Bars` расходуют одну квоту этого метода; нельзя считать, что каждому инструменту положены собственные 200. Точный учёт квоты для сессий/токенов проверяется на подключении; искусственное размножение токенов не является способом масштабирования. [Лимиты Finam](https://api.finam.ru/getting-started/chto-delat-kogda-api-otvechaet-ne-tak/limity-zaprosov/).

Наш расчёт для примера: 20 инструментов, ряды 5m, 15m и 1h, один запрос на очередное закрытие каждого ряда:

```text
20 × (60/5 + 60/15 + 60/60) = 340 запросов в час
В среднем ≈ 5,7 запроса Bars в минуту
На общей границе часа: до 60 запросов Bars на обновление
```

Здесь не учтены прогрев, повторы, повторная сверка и дополнительные периоды. Это оценка числа запросов, не измерение задержек/возможностей сервера. Запросы на общей границе распределяются с ограничением параллелизма и резервом квоты. Число одинаковых сигналов не умножает запросы: несколько схем используют общий кеш ряда.

Для сравнения, опрос всех 60 рядов каждые 10 секунд потребовал бы 360 запросов в минуту. Такой наивный режим превышает опубликованный предел. Часовые и дневные данные не нужно заново запрашивать на каждом закрытии 5m.

## Ограничение закрытых свечей

В модели Bar отсутствует отдельный `isClosed`. Поле `is_data_snapshot` в опубликованном protobuf означает снимок данных, а не завершённость свечи. Один лишь успешный ответ `Bars` тоже не подтверждает финальность последнего бара. [Модель Bar](https://raw.githubusercontent.com/FinamWeb/finam-trade-api/main/proto/grpc/tradeapi/v1/marketdata/marketdata_service.proto).

Для потока BARS официальный рецепт предлагает хранить последнюю свечу как изменяемую до появления более позднего timestamp. Последний бар перед перерывом/концом сессии и задержки редких сделок требуют отдельной обработки. Для REST проверяется тот же инвариант отсутствия незакрытых входов, а не копируется допущение, что любой ответ исторического метода финален. [Рецепт завершённых свечей Finam](https://api.finam.ru/getting-started/bystryy-start/prakticheskie-recepty-nadezhnogo-klienta/).

Проверка перед live-приёмкой: сопоставить timestamp и календарь, поведение последнего бара в REST/потоке, задержку публикации и поздние изменения. До проверки нельзя обещать сигнал ровно в секунду границы периода. Политика стабилизации/повторной сверки задаётся адаптером; исходные данные и их ревизии сохраняются.

## REST и потоковые обновления

| Потребность | Оценка |
|---|---|
| График из истории, расчёты, бэктест | REST подходит |
| Сигналы после закрытия 5m и старших периодов | REST подходит при планировщике и проверке публикации/закрытия |
| Несколько периодов внутри одного И / ИЛИ | Выполняется локальным движком независимо от транспорта |
| Живое движение незакрытой свечи и цены каждую секунду | Предпочтительна подписка WebSocket/gRPC |
| Большое число инструментов или полная лента сделок | Проверка квот и потоковый транспорт; REST-снимки не гарантируют полноты ленты |

Finam рекомендует подписки для постоянных обновлений: WebSocket — для JSON-клиента, gRPC — для типизированного клиента и потока обновления access key. Это выбор транспорта внутри DataProvider, без изменений схем и Telegram. [Рекомендации Finam](https://api.finam.ru/getting-started/bystryy-start/diagnostika-oshibok-i-dalneyshie-shagi/).

## Что остаётся проверить с реальным доступом

- Какие инструменты доступны токену, включая нужный вариант EUR/USD; есть ли задержка данных и пригодный объём для выбранных условий.
- За какое время после ожидаемой границы `Bars` возвращает актуальную завершённую свечу.
- Как завершается последний бар сессии и обрабатываются неторговые интервалы.
- Фактические ограничения интервала/размера ответа, срок токена и восстановление авторизации.
- Всплески общей границы часа, восстановление истории и повторная сверка укладываются в квоты с резервом.

Смена REST polling на поток меняет получение данных внутри адаптера, но не SignalDefinition, вычислитель условий, SignalEvent или NotificationChannel.
