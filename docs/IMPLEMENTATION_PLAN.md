# План реализации TradeMaster по фазам

> Актуальное упрощение конструктора: [CURRENT_SIGNALS.md](CURRENT_SIGNALS.md). Пять индикаторов, группы И / ИЛИ, без временных окон и цепочек; две начальные схемы вверх / вниз. Прежние описания этих возможностей ниже относятся к предыдущему объёму.

Дата: 4 ноября 2026 года. Статус: реализация идёт; работает первая desktop-вертикаль, продолжается фаза 2. Проверенный результат и незавершённые пункты: [IMPLEMENTATION_STATUS.md](IMPLEMENTATION_STATUS.md).

Ограничение: доступ к Finam ожидается **5 ноября 2026 года**. До этого разработка идёт на воспроизводимых локальных данных через тот же контракт поставщика, который будет реализован Finam. Появление доступа — условие проверки интеграции, а не обещание закончить предыдущие фазы за один день.

В план включён второй реальный поставщик — **iTick, REST + WebSocket**. Подготовка адаптера и контрактных тестов не требует работающего Finam; проверка iTick с реальным ключом начинается при появлении соответствующего доступа, независимо от даты доступа к Finam. Детали: [ITICK.md](ITICK.md).

## Принципы выполнения

- Первая рабочая сущность — валютная пара с её графиком и сигналами.
- Сначала собираем небольшой сквозной рабочий сценарий, затем расширяем возможности конструктора. README — пример регрессионной схемы, а не фиксированный алгоритм продукта.
- Используем выбранные готовые компоненты: Ant Design, React Query Builder, KLineCharts. Разрабатываем связи между ними и предметную логику сигналов.
- Автотесты критического контура пишутся в каждой фазе вместе с кодом. Отдельного этапа «когда-нибудь покроем сигнал тестами» нет.
- Синтетические данные проверяют корректность реализации. Они не подтверждают качество реального API, совпадение с TradingView или торговую результативность.
- Finam не импортируется в core, конструктор и Telegram. Реальная интеграция подключается заменой поставщика, без второго варианта движка.

- Зафиксировать контракты DataProvider, свечи/метаданных/календаря, схемы, события и канала уведомлений. Формат схем не зависит от внутреннего JSON UI-библиотеки.
- Сразу разделить Pair/Connection/InstrumentBinding и datasetId; создать реестр с описаниями настроек и общий MarketDataService/ChartBridge. Переключатель источника пары строится из реестра. Проверить дизайн контракта на тестовом REST-only источнике без каталога/объёма, чтобы ограничения Finam/iTick не стали обязательными для всех следующих API. Контракт: [DATA_SOURCES.md](DATA_SOURCES.md).
- Настроить Vitest и CI. Подготовить ручные эталонные свечи и ожидаемые результаты без генерации ожиданий проверяемым алгоритмом.
- Проверить возможность отрисовать рассчитанный в core нестандартный индикатор через KLineCharts, включая MACD WMA/WMA; не строить весь UI до проверки этого соединения.

Готовность: приложение запускается; компоненты совместимы; тесты запускаются одной командой; библиотечный график отображает локальный ряд и переданное значение индикатора. Проверка Windows выполняется в Windows-среде/CI: сборка на Mac не считается доказательством работоспособности Windows.

## Фаза 1. Первая рабочая вертикаль без биржи

Работы:

- Реализовать локальный ReplayProvider: история и обновления одной явно обозначенной тестовой пары, управляемое время, обновления открытой и закрытой свечи.
- Собрать главный экран: пары слева, график по центру, сигналы пары справа, события снизу. Внешний вид — штатные компоненты с небольшой настройкой темы.
- Добавить сохранение пары, простого сигнала и событий. Первый вычисляемый сценарий — кросс EMA на одном периоде; события получаются из engine, а не из заранее расставленных UI-заглушек.
- Реализовать общий мониторинг и индивидуальный переключатель сигнала: пауза, прогрев, новое выполнение, независимое обновление графика.
- Добавить тестовый канал уведомлений, который принимает события и показывает результат локально, без отправки в настоящий Telegram.

Готовность: можно запустить replay, видеть изменяемую свечу, получить ровно одно ожидаемое событие на закрытой свече и остановить/возобновить мониторинг. Есть отрицательный тест по незакрытому бару, тест дедупликации и тест отключённого сигнала. Везде явно указан источник «Тестовые данные».

- Реализовать типизированные выражения, вложенные И / ИЛИ и true/false/unknown, с объяснением каждого условия.
- Реализовать события/состояния, поиск по прошлому, временные этапы, параллельные подтверждения, фиксацию/перепроверку, сбросы, cooldown и категории результата.
- Реализовать согласованную оценку разных периодов, календарь, агрегацию 10m и отсутствие будущих данных.
- Добавить несколько эталонных схем: простой сигнал, смешанные И / ИЛИ, смешанные периоды, цепочка по мотивам README и варианты политик подтверждения. Каждый пример имеет явную конфигурацию; спорные настройки не становятся глобальным поведением.
- Реализовать checkpoint и детерминированное восстановление состояния.

Готовность: проходят проверки отдельных блоков, схем и их совместной работы. Результаты изолированного/совместного прогона и пошагового replay/истории совпадают. Проверены равенства на границах, таймауты, перестановки входных сообщений, несколько пар, пропуски, сбросы и отсутствие влияния открытых/будущих свечей. Матрица обязательных сценариев — [SPEC.md, раздел 13.2](SPEC.md#132-обязательные-тесты-сигналов).

## Фаза 4. Реальные поставщики — при появлении доступа

### 4А. Finam

Эту фазу начинаем **5 ноября или позднее, как только доступ фактически получен**. Секрет вводится в локальных настройках/среде проверки, не в документации и не в репозитории.

Порядок проверки:

1. Авторизация, срок/обновление сессии, права на рыночные данные и задержка.
2. Справочник: найти первый реально доступный валютный инструмент; проверить код, площадку, календарь, единицы и наличие пригодного объёма. EUR/USD остаётся примером до проверки.
3. REST Bars: загрузить разные периоды, проверить глубину/размер выдачи, timestamp, расписание и пропуски.
4. WebSocket BARS: подключить один инструмент/период, сшить историю и поток, проверить обновления текущего бара и переподключение.
5. Проверить завершение свечей, включая последнюю свечу сессии, задержки публикации и поздние исправления. Зафиксировать политику адаптера и интеграционные примеры.
6. Проверить лимитер, всплески общих закрытий и восстановление после обрыва. Сохранить обезличенные ответы в контрактные фикстуры без секретов и приватных сведений.
7. Подключить Finam через DataProvider и прогнать те же схемы. Контрактные тесты сравнивают одинаковые нормализованные входы; различные реальные котировки не обязаны давать прежние события синтетики.

Готовность: есть проверенный адаптер и запись фактических возможностей/ограничений. Смена ReplayProvider на Finam не требует изменения AST, конструктора или Telegram. До подтверждения корректного закрытия свечей real-live сигналы не принимаются как готовая функция.

Если доступ задержится: продолжаются фазы 0–3 и офлайн-часть 5. Если нет объёма, истории или нужного инструмента: фиксируется ограничение и показывается несовместимость; правила схем не изменяются молча.

### 4Б. iTick — альтернативный REST/WebSocket

До получения ключа: подготовить адаптер и фикстуры каталога, tick/kline, ответов авторизации и свечного потока. Общий DataProvider уже используется в UI и core; отдельная реализация индикаторов для iTick не создаётся.

С реальным доступом:

1. Проверить окружение trial/production, заголовок token и фактические квоты/задержки.
2. Загрузить `/symbol/list?type=forex&region=GB`, связать c/n/t/e с общим каталогом; проверить поиск пары и ручной ввод по code.
3. Подключить `/forex/kline`, проверить периоды, пагинацию et/limit, глубину истории, timestamp, объём и завершение свечи. REST tick используется для цены, а не как замена полной истории.
4. Подключить forex WebSocket, проверить права на kline, heartbeat, subscribe/unsubscribe, восстановление и сверку. Если тариф не даёт kline, явно отметить ограничение; не выдавать поток quote за полноценные свечи.
5. Выполнить общие контрактные тесты и сквозные сценарии сигналов. REST- и WS-коды прикладного успеха, источники/окружения кеша и единицы объёма проверяются раздельно.

Готовность: iTick выбирается как источник пары; тот же редактор и engine работают с ним без изменений логики. Переключение Finam ↔ iTick выполняет новый прогрев, не смешивает историю и не меняет Telegram-настройки. Автоматическое аварийное переключение поставщика в первой версии не требуется. Требования: [ITICK.md](ITICK.md).

## Фоновый мониторинг и питание

Мониторинг работает в utility process и не зависит от выбранного экрана или свёрнутого окна. При общем мониторинге и хотя бы одном включённом сигнале main process запрашивает у ОС запрет автоматического сна (`prevent-app-suspension`); выключение дисплея разрешено. При паузе, выключении последнего сигнала, удалении последних отслеживаемых пар, остановке движка и выходе блокировка снимается.

После системного `resume` заново загружается история и создаются подписки на данные, переподключается бот и возобновляется обработка сохранённой очереди Telegram. Контрольные точки сигналов сохраняются в памяти; доступные пропущенные закрытия проверяются существующим механизмом, разрывы данных не подменяются вымышленными свечами.

Запрет автосна не гарантирует работу при ручном сне, закрытой крышке ноутбука, гибернации, выключении или отсутствии сети. Во время полного сна вычисления и отправка не выполняются. Для круглосуточной работы независимо от состояния ПК требуется отдельный серверный процесс мониторинга; он пока не реализован. Проверка обработки `resume` не заменяет физическую проверку сна и питания на целевых macOS/Windows.
