# TradeMaster

Проект desktop-терминала для Finam с расширяемыми источниками данных, конструктором сигналов И / ИЛИ, условиями на разных таймфреймах и уведомлениями в Telegram.

Источники данных: **Finam и iTick**, каждый через собственный адаптер REST/WebSocket.

Рабочая версия: Node.js 22.12+, `npm install`, затем `npm start`. Для разработки — `npm run dev`; проверки — `npm test`, `npm run test:desktop`, `npm run test:editor`, `npm run test:temporal`. Ключи iTick и Finam вводятся в настройках приложения. Без ключа доступен Replay с явно обозначенными тестовыми данными. Telegram привязывается в настройках через бота; Finam подключён через REST/WebSocket; подробности и ограничения — в [FINAM_REST.md](docs/FINAM_REST.md).

Сборка установщика: `npm run package:mac` на macOS или `npm run package:win` на Windows. Проверка готового приложения — `npm run package:verify`. Подпись, нотариализация и установка: [инструкция по сборке](docs/BUILD.md).

Telegram: сохранить токен → «Привязать через бота» → в Telegram «Старт» и «Подписаться». Chat ID заполняется автоматически. После привязки можно отправить тест из настроек; в боте доступны «Подписаться» / «Отписаться». Для смены бота нажмите «Заменить» и повторите привязку. Бот и мониторинг работают, пока TradeMaster открыт.

# Сигналы: цепочка подтверждений

  

SUI/USDC, 5m. Проверка только на **закрытой** свече. `i` — текущая закрытая свеча.


**Порядок анализа:**

  

```

ШАГ 1. КРОСС EMA 5/10 → триггер, с него начинается цепочка

↓

ШАГ 2. ПОДТВЕРЖДЕНИЕ → СТОХАСТИК ─┐

(параллельно) ├─ оба в окне 3 свечей

MACD ──────┘

↓

ШАГ 3. ФОН + ОБЪЁМ → определяет силу сигнала

```

  

Стохастик и MACD анализируются **параллельно**, не по очереди: оба должны

подтвердить разворот в общем окне 3 свечей после кросса. Порядок между ними

не важен — кто-то сработает раньше, кто-то позже.

  

Не подтвердили оба за 3 свечи — цепочка рвётся, ждём нового кросса.

  

---

  

Экспорт и импорт доступны в **Настройки → Экспорт и импорт**; отдельный сигнал экспортируется из его карточки. [Состав файлов и режимы импорта](docs/CONFIGURATION_TRANSFER.md).

## Общие понятия

  

**Кросс EMA** — пересечение быстрых средних, точка отсчёта любой цепочки:

- медвежий: `ema5[i-1] >= ema10[i-1]` и `ema5[i] < ema10[i]`

- бычий: `ema5[i-1] <= ema10[i-1]` и `ema5[i] > ema10[i]`

  

**Пролив и отскок.** От кросса отсчитываем назад до локального экстремума

в окне 20 свечей.

- *Пролив* — движение до кросса.

- *Отскок* — от кросса до текущей свечи.

  

Сравниваем **средний объём** на участках: `объём отскока` / `объём пролива`.

**Фон** — направление медленных средних: `ema30` и `ema90` против своих значений

3 свечи назад.

# ЦЕПОЧКА A. Разворот вниз

Триггер — медвежий кросс EMA 5 под EMA 10.

```

ШАГ 1 ШАГ 2 (параллельно) ШАГ 3

Кросс EMA 5↓10 → ┌─ Стохастик вниз → Фон + объём

(триггер) └─ MACD вниз → сила сигнала

оба в окне 3 свечей

┌─ фон ↓ + объём слаб

│ → Разворот вниз: подтверждён

└─ иначе

→ Разворот вниз: ранний

```

  

### Шаг 1 — триггер: кросс EMA 5/10 вниз

  

| Что происходит | Проверка |

|---|---|

| Быстрая EMA ушла под медленную | `ema5[i-1] >= ema10[i-1]` и `ema5[i] < ema10[i]` |

| Перед этим был рост | `close[i] > close[i-10]` ИЛИ `ema5[i-5] > ema5[i-10]` |

  

Запоминаем номер этой свечи — от неё считаются все окна.

  

Без кросса цепочка не начинается — это единственная точка входа.

  

### Шаг 2 — подтверждение: стохастик и MACD (параллельно)

  

Оба индикатора проверяются **независимо** в окне **3 свечи после кросса**.

Стохастик ищется чуть шире — от 3 свечей ДО кросса, так как осциллятор часто

разворачивается раньше.

  

**Подтверждение по стохастику** — окно от кросса−3 до кросса+3:

  

| Что происходит | Проверка |

|---|---|

| Был наверху | `%K >= 80` в окне |

| %K пересёк %D сверху вниз | `stoch_K[j-1] > stoch_D[j-1]` и `stoch_K[j] <= stoch_D[j]` |

| И продолжает снижаться | `stoch_K[i] < stoch_K[i-1]` |

  

**Подтверждение по MACD** — окно от кросса до кросса+3:

  

| Что происходит | Проверка |

|---|---|

| Гистограмма снижается | `hist[i] < hist[i-1]` |

| Линия MACD под сигнальной | `macd[i] < signal[i]` |

  

**Оба подтвердили** (в любом порядке, на любых свечах внутри своих окон) →

цепочка сложилась, переходим к оценке силы.

  

Хотя бы один не подтвердил за 3 свечи — **цепочка сброшена**.

  

### Шаг 3 — фон и объём: насколько верить

  

Проверяется на свече, где сложилось последнее из двух подтверждений.

  

| Условие | Результат |

|---|---|

| `ema30[i] < ema30[i-3]` и `ema90[i] < ema90[i-3]` **и** объём отскока < объём пролива × 0.8 | **«Разворот вниз: подтверждён»** |

| Любой другой расклад | **«Разворот вниз: ранний»** |

  

> **«Разворот вниз: подтверждён»:** слом структуры подтверждён фоном и объёмом.

> Все три шага сошлись.

  

> **«Разворот вниз: ранний»:** цепочка сложилась, но фон или объём против.

> Сигнал есть, доверия меньше.

# ЦЕПОЧКА B. Разворот вверх

  

Зеркально. Триггер — бычий кросс EMA 5 над EMA 10.

  

```

ШАГ 1 ШАГ 2 (параллельно) ШАГ 3

Кросс EMA 5↑10 → ┌─ Стохастик вверх → Фон + объём

(триггер) └─ MACD вверх → сила сигнала

оба в окне 3 свечей

┌─ фон ↑ + объём силён

│ → Разворот вверх: подтверждён

└─ иначе

→ Разворот вверх: ранний

```

  

### Шаг 1 — триггер: кросс EMA 5/10 вверх

  

| Что происходит | Проверка |

|---|---|

| Быстрая EMA вышла над медленной | `ema5[i-1] <= ema10[i-1]` и `ema5[i] > ema10[i]` |

| Перед этим было падение | `close[i] < close[i-10]` ИЛИ `ema5[i-5] < ema5[i-10]` |

  

Запоминаем номер свечи — от неё считаются окна.

  

### Шаг 2 — подтверждение: стохастик и MACD (параллельно)

  

**Подтверждение по стохастику** — окно от кросса−3 до кросса+3:

  

| Что происходит | Проверка |

|---|---|

| Был внизу | `%K <= 20` в окне |

| %K пересёк %D снизу вверх | `stoch_K[j-1] < stoch_D[j-1]` и `stoch_K[j] >= stoch_D[j]` |

| И продолжает расти | `stoch_K[i] > stoch_K[i-1]` |

  

**Подтверждение по MACD** — окно от кросса до кросса+3:

  

| Что происходит | Проверка |

|---|---|

| Гистограмма растёт | `hist[i] > hist[i-1]` |

| Линия MACD над сигнальной | `macd[i] > signal[i]` |

  

**Оба подтвердили** → переходим к оценке силы.

Хотя бы один не подтвердил за 3 свечи — **цепочка сброшена**.

  

### Шаг 3 — фон и объём

  

| Условие | Результат |

|---|---|

| `ema30[i] > ema30[i-3]` и `ema90[i] > ema90[i-3]` **и** объём отскока > объём пролива × 1.2 | **«Разворот вверх: подтверждён»** |

| Любой другой расклад | **«Разворот вверх: ранний»** |

## Жизнь цепочки

  

В каждый момент времени может быть по одной активной цепочке на направление:

одна «вниз» и одна «вверх». Про каждую помним: на какой свече был кросс,

какой шаг уже пройден, на каких свечах сработали стохастик и MACD.

  

**Правила:**

  

| Событие | Действие |

|---|---|

| Кросс EMA в направлении D | Новая цепочка D, старая цепочка D затирается |

| Стохастик подтвердил | Отмечаем в цепочке, ждём MACD (если ещё не было) |

| MACD подтвердил | Отмечаем в цепочке, ждём стохастик (если ещё не было) |

| Оба подтвердили | Переход к шагу 3, фиксация события |

| **Событие зафиксировано** | **Цепочка закрыта и сброшена** |

| Прошло 3 свечи, подтвердил только один | Цепочка сброшена |

| Обратный кросс EMA | Цепочка текущего направления сброшена |

  

После фиксации события цепочка закрывается — повторно то же событие она не

выдаёт. Новое возможно только с нового кросса EMA.

  

Обратный кросс — важное правило: если `ema5` вернулась обратно, исходная

предпосылка отменилась, и ждать подтверждений дальше бессмысленно.

## Таблица окон

  

| Что | Окно | При истечении |

|---|---|---|

| Стохастик после кросса | 3 свечи | сброс цепочки |

| Стохастик до кросса (поиск назад) | 3 свечи | — |

| MACD после кросса | 3 свечи | сброс цепочки |

| Фон и объём | на свече последнего подтверждения | — |

  

Полный цикл цепочки: от 1 до 4 свечей (5–20 минут на 5m).

  

Минимум 1 свеча: кросс, стохастик и MACD сложились одновременно.

Максимум 4: кросс, затем последнее из подтверждений на 3-й свече после.

## Логика в одной схеме

  

```

┌──────────────────────────┐

│ Закрылась свеча │

└────────────┬─────────────┘

↓

┌──────────────────────────┐

│ Пересчёт индикаторов │

│ (прогрев ≥ 110 свечей) │

└────────────┬─────────────┘

↓

┌──────────────────────────┐

│ Есть кросс EMA 5/10? │──── нет ──┐

└────────────┬─────────────┘ │

да ↓ ↓

┌──────────────────────────┐ ┌───────────────────┐

│ Старт цепочки │ │ Есть активная │

│ (вниз или вверх) │ │ цепочка? │

└────────────┬─────────────┘ └────────┬──────────┘

└──────────┬───────────────┘

↓

┌─────────────────┴─────────────────┐

↓ ПАРАЛЛЕЛЬНО ↓

┌──────────────────┐ ┌──────────────────┐

│ Стохастик │ │ MACD │

│ подтвердил? │ │ подтвердил? │

└────────┬─────────┘ └────────┬─────────┘

└──────────────┬──────────────────┘

↓

┌───────────────────────┐

│ Оба подтвердили? │── нет → ждём

└───────────┬───────────┘ (3 свечи, затем сброс)

да ↓

┌───────────────────────┐

│ Шаг 3: фон + объём │

│ → подтверждён / ранний│

└───────────────────────┘

```

  

**Принцип:** кросс EMA задаёт **когда смотреть**, стохастик и MACD —

**подтверждают ли разворот**, фон и объём — **насколько верить**.

## Индикаторы

  

| Индикатор | Параметры | Роль |

|---|---|---|

| EMA 5, EMA 10 | по `close` | **триггер цепочки** (кросс) |

| EMA 30, EMA 90 | по `close` | фон, шаг 3 |

| Стохастик | 10 / 5 / 5 | шаг 2, пороги 80 / 20 |

| MACD | 6 / 8 / 4, **обе MA — WMA** | шаг 2 (параллельно со стохастиком) |

| Объём + SMA | 9 | шаг 3 |

  

### Точные настройки (сверено с графиком)

  

**Стохастик:**

  

| Поле | Значение |

|---|---|

| %K Length | 10 |

| %K Smoothing | 5 |

| %D Smoothing | 5 |

  

Расчёт: `%K_raw` = положение `close` в диапазоне последних 10 свечей →

сглаживается SMA(5) → это `%K`; `%D` = SMA(%K, 5).

  

**MACD:**

  

| Поле | Значение |

|---|---|

| Длина Fast | 6 |

| Длина Slow | 8 |

| Данные | закр (`close`) |

| Длина сигнала | 4 |

| Oscillator MA Type | **WMA** |

| Signal Line MA Type | **WMA** |

  

Расчёт: `macd` = WMA(close, 6) − WMA(close, 8); `signal` = WMA(macd, 4);

`hist` = macd − signal.

  

**WMA в обоих полях** — и для основных линий, и для сигнальной.

  

Это важно при реализации: библиотеки по умолчанию считают MACD на EMA, и

такой расчёт не сойдётся с графиком. Нужна взвешенная средняя — веса 1..n,

где свежая свеча весит больше всех.

  

```

WMA(n)[i] = (close[i]·n + close[i-1]·(n-1) + ... + close[i-n+1]·1) / (n + (n-1) + ... + 1)

```

  

**Прогрев:** 110 свечей (упирается в EMA 90).

  

**Настраиваемые пороги:** `80` / `20` (стохастик), `0.8` / `1.2` (объём),

`3` (окно фона), `20` (окно пролива), `3` (окно подтверждения),

`3` (поиск стохастика назад).

## Что отлаживать в первую очередь

  

1. **Окно подтверждения (3 свечи).** Взято по логике, не по данным. В бэктесте

посмотреть реальное распределение: за сколько свечей после кросса обычно

разворачивается стохастик и подтверждает MACD. Слишком узкое окно режет

валидные цепочки, слишком широкое связывает несвязанные события.

  

2. **Порог стохастика `80` / `20`.** На 5m осциллятор заходит в зоны часто.

Возможно, для триггерной схемы он избыточно строг — проверить вариант

без требования захода в зону, только по факту пересечения %K/%D.

  

3. **Окно поиска стохастика назад (`3` свечи).** Разворот осциллятора часто

опережает кросс EMA. Измерить типичный лаг.

  

4. **Доля «ранних» против «подтверждённых».** Если «подтверждённых» почти нет —

условия шага 3 слишком строгие.

## Назначение

  

Система — **индикатор события**, не более. Её задача: зафиксировать, что

цепочка условий сложилась, и сообщить об этом с указанием, какие именно

условия совпали и с какими значениями.

  

Что делать дальше — решает человек. Система не даёт оценок, не предлагает

действий, не торгует.

  

Формулировка сообщения — описательная: «цепочка сложилась, шаги 1–3 пройдены,

фон нисходящий, объём отскока 0.62× от пролива». Не «сигнал на продажу».



# ТЗ: движок сигналов по индикаторам (SUI/USDC, 5m)

  

**Версия:** 1.0

**Дата:** 2026-09-16

**Статус:** черновик, источник данных уточняется

  

---

  

## 1. Назначение и границы

  

### 1.1 Что делает система

  

Читает свечи (OHLCV), считает по ним набор технических индикаторов, проверяет

условия четырёх именованных паттернов и при совпадении отправляет уведомление

в Telegram и пишет запись в лог.

  

### 1.2 Чего система НЕ делает

  

Это критично зафиксировать в ТЗ, чтобы не было расхождения ожиданий:

  

- **Не торгует.** Ордера на биржу не выставляются. Никаких API-ключей с правом

торговли в системе нет и быть не должно.

- **Не прогнозирует цену.** Детектируется совпадение формальных условий, а не

будущее движение. Срабатывание паттерна — это «условия совпали», а не

«цена пойдёт туда».

- **Не даёт рекомендаций.** Формулировки в уведомлениях — описательные

(«условия паттерна X совпали»), не императивные («покупай»).

  

### 1.3 Обязательное требование к приёмке

  

Система не считается готовой без **модуля бэктеста** (раздел 8). Паттерн,

не проверенный на истории, не имеет измеренной ценности: неизвестно, отличается

ли его результат от случайного входа. Бэктест входит в объём работ, а не в

«потом посмотрим».

  

---

  

## 2. Входные данные

  

### 2.1 Формат свечи

  

Канонический внутренний формат — один бар:

  

```python

@dataclass(frozen=True)

class Candle:

open_time: int # unix ms, время ОТКРЫТИЯ бара

open: Decimal

high: Decimal

low: Decimal

close: Decimal

volume: Decimal # объём в базовой валюте (SUI)

closed: bool # True = бар закрыт и финален

```

  

**Denominация объёма** (базовая валюта vs quote) фиксируется в конфиге

провайдера и не меняется между бэктестом и live — иначе пороги по объёму

разъедутся.

  

### 2.2 Абстракция источника

  

Источник данных на момент написания ТЗ не выбран. Логика индикаторов и

паттернов **не должна знать**, откуда пришли свечи. Интерфейс:

  

```python

class CandleSource(Protocol):

def history(self, symbol: str, interval: str, limit: int) -> list[Candle]:

"""Исторические закрытые свечи, по возрастанию open_time."""

  

def stream(self, symbol: str, interval: str) -> Iterator[Candle]:

"""Поток обновлений; отдаёт и незакрытые бары с closed=False."""

```

  

Реализации подключаются как плагины. Минимум один (файловый) нужен для

бэктеста, второй (биржевой) добавляется при выборе источника.

  

### 2.3 Требования к качеству данных

  

Перед расчётом индикаторов данные валидируются:

  

| Проверка | Действие при нарушении |

|---|---|

| Монотонность `open_time` по возрастанию | Ошибка, остановка обработки |

| Отсутствие дублей по `open_time` | Дедупликация, последний выигрывает |

| Пропуски баров (gap > 1 интервала) | WARN в лог + флаг `has_gaps` в контексте |

| `high >= max(open, close)`, `low <= min(open, close)` | Ошибка, бар отбрасывается |

| `volume >= 0` | Ошибка, бар отбрасывается |

  

**Пропуски критичны:** EMA — рекурсивный индикатор, дырка в данных искажает

все последующие значения. При обнаружении gap в окне прогрева паттерны на

этом участке не детектируются.

## 3. Индикаторы

  

Параметры взяты с графика пользователя (TradingView, Bybit SUI/USDC 5m).

Все периоды выносятся в конфиг, значения ниже — дефолты.

  

### 3.1 EMA (4 штуки)

  

```

EMA(n)[i] = close[i] * k + EMA(n)[i-1] * (1 - k), где k = 2 / (n + 1)

```

  

Периоды: **5, 10, 30, 90**, все по `close`.

  

**Инициализация:** первое значение = SMA первых `n` баров. Это соответствует

поведению TradingView. Расхождение в инициализации — самая частая причина

несовпадения с графиком.

  

### 3.2 MACD (6, 8, 4) на WMA

  

Сверено с настройками графика:

  

| Поле | Значение |

|---|---|

| Длина Fast | 6 |

| Длина Slow | 8 |

| Данные | `close` |

| Длина сигнала | 4 |

| Oscillator MA Type | **WMA** |

| Signal Line MA Type | **WMA** |

  

WMA стоит в **обоих** полях — и для основных линий, и для сигнальной.

  

При реализации: библиотеки по умолчанию считают MACD на EMA, такой расчёт

не сойдётся с графиком. Нужна взвешенная средняя (веса 1..n).

  

```

WMA(n)[i] = sum(close[i-n+1..i] * weights) / sum(weights), weights = 1..n

macd_line = WMA(6) - WMA(8)

signal_line = WMA(macd_line, 4)

histogram = macd_line - signal_line

```

  

### 3.3 Стохастик (10, 5, 5)

  

```

%K_raw = 100 * (close - min(low, 10)) / (max(high, 10) - min(low, 10))

%K = SMA(%K_raw, 5) # сглаживание

%D = SMA(%K, 5) # сигнальная линия

```

  

Деление на ноль (когда `max(high) == min(low)`, плоский участок): результат

`50.0`, а не `NaN` — иначе флэт ломает расчёт.

  

Пороги: перекупленность **≥ 80**, перепроданность **≤ 20** (конфигурируемо).

  

### 3.4 Объём

  

```

vol_sma = SMA(volume, 9)

```

  

### 3.5 Фракталы Билла Вильямса (период 2)

  

Верхний фрактал на баре `i`: `high[i]` строго больше `high` двух баров слева

и двух справа. Нижний — зеркально по `low`.

  

**Важно:** фрактал подтверждается только через 2 бара после экстремума.

В live-режиме это означает лаг в 2 бара — учитывать при детекте, не

использовать несформированный фрактал.

  

### 3.6 Требование к точности

  

Реализация должна совпадать с TradingView **с точностью 1e-6** на контрольном

наборе данных. Проверяется тестом (раздел 9.1). Считать вручную, без внешних

TA-библиотек — их дефолты по инициализации часто отличаются от TV.

  

### 3.7 Прогрев

  

Минимум баров до первого валидного сигнала:

  

```

warmup = max(90 (EMA90), 10+5+5 (стох), 8+4 (MACD), 9 (vol)) + 20 запаса = 110

```

  

До накопления `warmup` баров детект не запускается.

## 4. Общие правила детекта

  

### 4.1 Только закрытые бары

  

Паттерн проверяется **исключительно на закрытых барах** (`closed=True`).

Незакрытый бар меняется в реальном времени: условие может совпасть и

развалиться до закрытия. Детект на живом баре даст поток ложных алертов.

  

### 4.2 Отсутствие заглядывания в будущее

  

На баре `i` доступны только данные `[0..i]`. Это требование распространяется

и на бэктест — нарушение делает его результаты бессмысленными.

  

### 4.3 Дедупликация

  

Один паттерн на одном символе не может сработать повторно, пока не пройдёт

**cooldown = 6 баров** (30 минут на 5m) с последнего срабатывания.

Настраивается per-pattern.

  

### 4.4 Направление объёма

  

Для условий «объём пролива» и «объём отскока» вводятся понятия:

  

```python

def leg_volume(candles, start_idx, end_idx) -> Decimal:

"""Средний объём на участке [start_idx, end_idx]."""

```

  

- **Пролив (impulse leg)** — последовательность баров от локального максимума

до локального минимума в окне `lookback`.

- **Отскок (bounce leg)** — от этого минимума до текущего бара.

  

Границы находятся по экстремумам в окне `lookback = 20` баров.

## 5. Паттерны

  

Четыре независимых правила. Каждое детектится отдельно, у каждого свой набор

условий и свой cooldown.

  

### 5.1 `EXHAUSTION_BEARISH` — истощение импульса вверх

  

Соответствует скриншоту 1: рост упёрся, осциллятор в перекупленности, объём

не подтверждает.

  

| # | Условие | Формализация |

|---|---|---|

| 1 | Стохастик в перекупленности | `%K[i-1] >= 80` |

| 2 | Разворот %K вниз через %D | `%K[i-1] > %D[i-1] and %K[i] <= %D[i]` |

| 3 | MACD-гистограмма краснеет | `hist[i] < hist[i-1] and hist[i-2] > hist[i-3]` (перелом) |

| 4 | Рост на падающем объёме | `volume[i] < vol_sma[i]` и объём растущей ноги ниже среднего |

| 5 | Был рост | `close[i] > close[i-5]` |

  

Срабатывает при выполнении **всех пяти**.

  

### 5.2 `BOUNCE_WEAK` — слабый отскок в нисходящей структуре

  

Соответствует скриншоту 2: цена отскочила, но структура нисходящая и объём

отскока слабее объёма пролива. Технический отскок, не разворот.

  

| # | Условие | Формализация |

|---|---|---|

| 1 | Пробой быстрых EMA снизу вверх | `close[i] > ema5[i] and close[i] > ema10[i]` и `close[i-1] <= ema5[i-1]` |

| 2 | MACD развернулся вверх | `hist[i] > 0 and hist[i-1] <= 0` ИЛИ `macd[i] > signal[i] and macd[i-1] <= signal[i-1]` |

| 3 | **Медленные EMA падают** | `ema30[i] < ema30[i-3] and ema90[i] < ema90[i-3]` |

| 4 | **Объём отскока слабее пролива** | `leg_volume(bounce) < leg_volume(impulse) * 0.8` |

| 5 | Предшествовало снижение | `min(low[i-20..i]) < ema90[i-20] * 0.997` |

  

Порог `0.8` в условии 4 — конфигурируемый.

  

### 5.3 `BOUNCE_STRONG` — отскок с подтверждением

  

Зеркало 5.2: те же условия 1, 2, 5, но **медленные EMA растут** и **объём

отскока сильнее пролива**.

  

| # | Условие | Формализация |

|---|---|---|

| 1 | Пробой быстрых EMA снизу вверх | как в 5.2 |

| 2 | MACD развернулся вверх | как в 5.2 |

| 3 | **Медленные EMA растут** | `ema30[i] > ema30[i-3] and ema90[i] > ema90[i-3]` |

| 4 | **Объём отскока сильнее пролива** | `leg_volume(bounce) > leg_volume(impulse) * 1.2` |

| 5 | Предшествовала коррекция | `min(low[i-20..i]) < ema30[i-20]` |

  

### 5.4 `EXHAUSTION_CONFIRMED` — истощение с подтверждением структуры

  

Расширение 5.1: те же условия плюс **EMA 5/10 развернулись вниз после роста**,

**EMA 30/90 падают**, **объём отскока слабее объёма пролива**.

  

| # | Условие | Формализация |

|---|---|---|

| 1-5 | Все условия `EXHAUSTION_BEARISH` | см. 5.1 |

| 6 | Быстрые EMA вниз после роста | `ema5[i] < ema5[i-1] and ema10[i] < ema10[i-1]` и `ema5[i-5] > ema5[i-6]` |

| 7 | Медленные EMA падают | `ema30[i] < ema30[i-3] and ema90[i] < ema90[i-3]` |

| 8 | Объём отскока слабее пролива | `leg_volume(bounce) < leg_volume(impulse) * 0.8` |

  

Это самый строгий паттерн — срабатывать будет заметно реже остальных.

  

### 5.5 Конфигурация паттернов

  

Все пороги (`80`, `0.8`, `1.2`, `0.997`, окна `3`, `5`, `20`) выносятся в

YAML-конфиг, не хардкодятся:

  

```yaml

patterns:

BOUNCE_WEAK:

enabled: true

cooldown_bars: 6

slow_ema_lookback: 3

volume_ratio_max: 0.8

impulse_lookback: 20

```

### 7.1 Принципы

  

- **Индикаторы — чистые функции.** `list[Candle] -> list[Decimal]`. Без

состояния, без IO. Это делает их тестируемыми и переиспользуемыми в

бэктесте без изменений.

- **Паттерн — чистый предикат.** `(IndicatorContext, index) -> PatternMatch | None`.

- **Один и тот же код паттернов** работает в live и в бэктесте. Если код

расходится — бэктест не проверяет то, что реально работает.

- **Decimal, не float** для цен. На пятом знаке в 0.6873 ошибки округления

float дают ложные срабатывания на сравнениях.

  

### 7.2 Стек

  

- Python 3.12+

- `uv` для зависимостей (совпадает с практикой в Ace)

- `pandas` допустим для бэктеста, но **не в ядре индикаторов** — там ручной

расчёт ради контроля над формулами и точного совпадения с TradingView

- `httpx` для Telegram

- `pydantic` для конфига

- `pytest` для тестов

## 8. Бэктест (обязательная часть)

  

### 8.1 Задача

  

Прогнать правила по истории и измерить, что происходило **после** каждого

срабатывания. Без этого движок — генератор алертов с неизвестной ценностью.

  

### 8.2 Метрики

  

Для каждого паттерна на выборке:

  

| Метрика | Описание |

|---|---|

| `count` | Сколько раз сработал |

| `freq_per_day` | Частота срабатываний |

| `mfe` | Max favorable excursion за N баров (N = 3, 6, 12, 24) |

| `mae` | Max adverse excursion за те же N |

| `close_delta_pct` | Изменение close через N баров, % |

| `win_rate_net` | Доля исходов лучше нуля **после вычета комиссии** |

| `median_move` | Медианное движение (не среднее — устойчиво к выбросам) |

  

### 8.3 Комиссия — обязательно в расчёте

  

```yaml

backtest:

taker_fee_pct: 0.055 # Bybit taker, уточнить актуальную

slippage_pct: 0.02 # проскальзывание

round_trip_cost_pct: 0.13 # вход + выход + проскальзывание

```

  

**Почему это критично именно здесь.** На разобранных скриншотах вся амплитуда

движения — 0.5–0.7%. Round-trip издержки ~0.13% съедают от пятой части до

четверти движения. Паттерн с «win rate 55%» до комиссии может оказаться

убыточным после неё. Метрика `win_rate_net` считается только после вычета

издержек; версия «до комиссии» в отчёт не выводится, чтобы не вводить в

заблуждение.

  

### 8.4 Baseline для сравнения

  

Отчёт **обязан** включать контрольную группу: те же метрики для **случайных

входов** в том же количестве на той же выборке.

  

Паттерн имеет ценность только если его метрики статистически значимо лучше

случайного входа. Если `win_rate_net` паттерна 52%, а случайного входа 51% —

паттерн не обнаружил ничего, кроме шума. Это главный вопрос, на который

отвечает бэктест.

  

### 8.5 Разделение выборки

  

- **In-sample** — на этих данных подбираются пороги

- **Out-of-sample** — минимум 30% данных, **не используются при подборе**

  

Результат на in-sample не является доказательством работоспособности: пороги

всегда можно подогнать под известную историю. Отчёт показывает обе цифры рядом.

  

### 8.6 Формат отчёта

  

Markdown + CSV с сырыми срабатываниями (timestamp, паттерн, цена, исходы

через N баров) для самостоятельного анализа.

## 9. Тестирование

  

### 9.1 Верификация индикаторов (критично)

  

Эталонный набор: 300 баров SUIUSDC 5m с известными значениями индикаторов,

снятыми с TradingView. Тест сверяет расчёт с эталоном с точностью `1e-6`.

  

Без этого теста нельзя доверять ничему: расхождение в формуле EMA или в

инициализации MACD делает все паттерны ложными, и обнаружится это не сразу.

  

### 9.2 Тесты паттернов

  

Для каждого из четырёх паттернов:

- Синтетический ряд, на котором паттерн **обязан** сработать

- Ряд, где совпадают 4 условия из 5 — **не должен** сработать

- Проверка cooldown: два подряд совпадения → одно срабатывание

  

### 9.3 Тесты данных

  

- Свеча с `high < close` → отбрасывается

- Пропуск баров → WARN + флаг

- Дубли по `open_time` → дедупликация

- Незакрытый бар → детект не запускается

  

### 9.4 Тест отсутствия заглядывания

  

Прогон бэктеста, где на каждом шаге движку физически передаётся срез

`candles[0..i]`. Результат обязан совпасть с полным прогоном. Расхождение =

где-то читается будущее.

4. **Актуальная комиссия Bybit** для вашего уровня — влияет на `win_rate_net`.

## 12. Замечание о таймфрейме

  

Фиксирую как часть ТЗ, потому что это влияет на ожидания от результата.

  

Паттерны описаны по 5-минутному графику, где на разобранных участках вся

амплитуда движения составляла 0.5–0.7%. На таком масштабе значительная часть

колебаний — микроструктурный шум, а не движение, которое индикаторы способны

описать. Параметры индикаторов на графике (MACD 6/8/4, EMA 5/10, стохастик

10/5/5) выбраны очень короткими и реагируют почти на каждый бар, что даёт

высокую частоту сигналов и низкое отношение сигнал/шум.

  

Архитектура ТЗ не привязана к 5m: интервал — параметр конфига. Рекомендую на

этапе 3 прогнать бэктест **параллельно на 5m, 15m и 1h** с одними и теми же

правилами и сравнить `win_rate_net` и baseline. Это дешёвая проверка, которая

даст фактический ответ вместо предположений, и может оказаться, что те же

условия на старшем таймфрейме работают заметно устойчивее.
